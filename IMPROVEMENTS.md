# BeamSim3D — Architecture Reference & Improvements Log

This document is written to be self-contained: a reader (human or AI) should be able to understand the entire system — what it does, how every piece fits together, exact formulas and configuration — without opening any source file. The second half is a running history of what was tried, what worked, and what didn't, with real numbers from actual runs.

## 1. What this project is

Three components, in order of how they build on each other:

1. **A C++ physics engine** (`ThrowSim.cpp`) that simulates a projectile thrown with a given velocity, mass, launch height, and wind, integrated frame by frame with gravity, drag, and a bounce off procedurally-generated rolling-hill terrain. It has a batch mode that generates a large dataset of randomized throws, and CLI modes for asking the real physics for ground truth on one specific throw.
2. **A PyTorch training pipeline** (`main.py` and supporting scripts) that trains a neural network on that dataset to predict where a thrown object will land — plus a self-estimate of how confident it is.
3. **A 3D game** (`ThrowGame.cpp`) that renders a throw live, animates the real physics alongside the AI's prediction, and lets a player compete against the AI (closest guess to the real landing spot wins), with target-zone scoring and persistent stats.

There's also a separate, earlier soft-body vehicle physics demo (`main.cpp`, `Physics.cpp`/`.h`, executable `beam_sim`) that predates the throw/ML side of the project and is unrelated to it — a mass-spring vehicle chassis rendered in its own raylib window.

## 3. The physics engine (`ThrowSim.cpp`)

### 3.1 Simulation

Fixed-timestep integration, `dt = 0.01s`, up to `maxSteps = 5000` (50 simulated seconds).

Per step:
```
ax = -dragCoeff * vx / mass + windAccel
ay = -gravity - dragCoeff * vy / mass
vx += ax * dt;  vy += ay * dt
x  += vx * dt;  y  += vy * dt
```
Constants: `gravity = 9.81`, `dragCoeff = 0.2`, `restitution = 0.4`, `groundFriction = 0.7`, `restEps = 0.05`.

`windAccel` is a **constant horizontal acceleration** applied every step for the whole flight (not velocity-relative drag) — the simplest physically-reasonable model of a steady crosswind.

Ground collision: `ground = terrainHeight(x)` (see 3.2). If `y <= ground`: a bounce is counted if the incoming `|vy| > 0.5` (see the gotcha in section 6 about why), then `y = ground`, `vy = -vy * restitution`, `vx *= groundFriction`, and `vy` snaps to exactly `0` if `|vy| < restEps`.

Rest condition (ends the simulation): `y == ground && |vy| < restEps && |vx| < restEps`. If this is never reached within `maxSteps`, the simulation just stops at the cap (see gotcha in section 6 about wind preventing settling).

Tracked throughout: `maxHeight` (peak `y` reached) and `apexTime` (sim time it was reached), `bounceCount` (real impacts only), `timeToLand` (sim time at rest, or the 50s cap).

### 3.2 Terrain (`Terrain.h`)

```
terrainHeight(x) = 2*sin(x*0.05) + 0.5*sin(x*0.13)
terrainSlope(x)  = 2*0.05*cos(x*0.05) + 0.5*0.13*cos(x*0.13)   // d/dx, used for rendering normals
```
Only varies with `x`, flat across `z`. This single function is shared by `ThrowSim.cpp` (physics) and `ThrowGame.cpp` (rendering) via the header so they can never disagree with each other.

### 3.3 Input ranges (`ThrowRanges.h`)

```
VX_MIN, VX_MAX         = -15.0, 65.0
VY_MIN, VY_MAX         = 5.0, 100.0
MASS_MIN, MASS_MAX     = 0.5, 20.0
HEIGHT_MIN, HEIGHT_MAX = 0.5, 20.0
WIND_MIN, WIND_MAX     = -3.0, 3.0
```
Shared by `ThrowSim.cpp` (dataset generation, uniform random sampling) and `ThrowGame.cpp` (player control clamping). A trained model is only meaningful for inputs inside the range it was trained on — if these two ever disagree, the game would let a player throw at values the model has never seen.

## 4. The model

### 4.1 Inputs (6 total fed to the network)

5 raw: `vx0, vy0, mass, height0, windAccel`, plus 1 engineered feature appended by `features.py`'s `add_engineered_features()`:

```
x_inf = vx0 * mass / DRAG_COEFF
```
The asymptotic horizontal range under pure exponential drag decay, ignoring wind/terrain/bounce/finite flight time (`DRAG_COEFF = 0.2`, must match `ThrowSim.cpp`'s `dragCoeff`) — the dominant factor driving `final_x`, so it gives the network a head start instead of learning that relationship from scratch. Indexes `vx0` at column 0, `mass` at column 2 of the raw 5-column input tensor before normalization, unaffected by `height0`/`windAccel` being appended after `mass`.

A second engineered feature, `physics_baseline_x` (an exact analytical wind-aware horizontal-displacement solution — see `features.py` for the formula), was tried as a 7th input and **reverted** — see section 8's "Physics-informed `final_x` baseline" entry for the full, resolved story (it regressed every output, not just x). The function is still defined in `features.py`, unused, for a future properly-controlled retry.

### 4.2 Outputs (8 total)

Indices 0–6 are real regression targets with a matching CSV column, trained with Huber loss:
```
0: final_x       1: final_y       2: maxHeight     3: timeToLand
4: bounceCount   5: apexTime      6: finalVx
```
Index 7 is a **log-variance uncertainty head** — not a regression target (no CSV column exists for it, since "the model's confidence" isn't a physical quantity `ThrowSim.cpp` can compute). See section 5.3 for how it's trained.

### 4.3 Architecture (`models/ImprovedNeuralNetwork.py`)

Feedforward, 9 hidden layers, ReLU → BatchNorm1d → Dropout after each:

| Layer | Shape | Dropout |
|---|---|---|
| fc1 | 6 → 250 | 0.05 |
| fc2 | 250 → 250 | 0.05 |
| fc3 | 250 → 250 | 0.05 |
| fc4 | 250 → 300 | 0.05 |
| fc5 | 300 → 450 | 0.05 |
| fc6 | 450 → 600 | 0.05 |
| fc7 | 600 → 1200 | 0.05 |
| fc8 | 1200 → 2000 | 0.05 |
| fc9 | 2000 → 2000 | 0.05 |
| fc10 (output) | 2000 → 8 | — (raw linear, no activation/BN/dropout) |

**Total parameters: 7,764,408.**

Dropout was originally `0.0000000001` on every layer — a typo that made it functionally inert (no real regularization beyond `weight_decay`). Fixed to `0.1`, then lowered to `0.05` after `0.1` measurably slowed convergence at a fixed epoch budget (see section 8) — real regularization, without paying as much convergence-speed cost.

## 5. Training (`main.py`)

### 5.1 Data pipeline

Loads `build/throw_results.csv`, plus `game_throws.csv` (real played throws logged by `ThrowGame.cpp`) concatenated on if present → builds a `(N, 5)` raw input tensor and `(N, 7)` target tensor → appends the 2 engineered features (→ `(N, 7)`) → splits **70/15/15 train/val/test**, shuffled with a fixed seed (`torch.manual_seed(42)`) → normalizes inputs to zero-mean/unit-variance using **train-set statistics only** (no leakage into val/test). **Targets are not normalized** — trained once, found to hurt more than help (see section 8).

Device: `mps` (Apple Silicon GPU) if available, else `cpu`. Checkpoint is always saved with CPU tensors regardless of training device, so it loads on any machine.

### 5.2 Mini-batching

Manual on-device batching, `batch_size = 2048`: each epoch, `torch.randperm(n_train, device=device)` shuffles indices on-GPU, then sliced into `n_train // batch_size` batches (the remainder is dropped — see gotcha in section 6, a trailing batch of exactly 1 sample crashes `BatchNorm1d` in train mode). Originally a `DataLoader`; replaced because it was shuffling/collating tensors that were already moved to `device` through CPU-side machinery for no reason — benchmarked ~15% faster per epoch with identical batch composition semantics. (A larger `batch_size=8192` + scaled-up `lr=0.0025` was also tried to cut wall-clock further — see section 8, it measurably backfired and was reverted.)

### 5.3 Loss

Two separate loss terms, summed for the backward pass:

```python
main_loss = HuberLoss(outputs[:, :7], targets)   # the 7 real targets

# outputs[:, 7] is a log-variance (log of the per-axis landing-position
# error variance). Trained via Gaussian NLL. The point-estimate outputs
# are DETACHED here so this loss only trains the uncertainty head — it
# doesn't also push back on x/y, which are already trained by main_loss.
xy_error_sq = (outputs[:, 0].detach() - targets[:, 0])**2 + (outputs[:, 1].detach() - targets[:, 1])**2
log_var = outputs[:, 7].clamp(-10.0, 10.0)
uncertainty_loss = mean(0.5 * exp(-log_var) * xy_error_sq + log_var)

loss = main_loss + uncertainty_loss   # this is what .backward() is called on
```
`weight_decay=1e-4` on Adam, `lr=0.001` initial.

Two bugs fixed in this loss (see section 8 for the full story):
- **`log_var` coefficient.** The correct 2D isotropic Gaussian NLL has `log_var` with coefficient 1 (it's a per-axis term, appearing once per axis: `log_var + 0.5*exp(-log_var)*(dx^2+dy^2)`). An earlier version used `0.5*log_var` (copied from the single-axis scalar NLL formula), which made the model converge to `exp(log_var) = E[dx^2+dy^2]` — double the true per-axis variance, i.e. reported uncertainty ~sqrt(2)x too large from this alone.
- **`log_var` clamping.** Without `.clamp(-10, 10)`, `log_var` can land on a large-negative raw value early in training, and `exp(-log_var)` explodes (observed: loss ~4.6e8 in the first 20 epochs). Because `log_var` isn't detached, that huge gradient flows back through `fc10` into the shared trunk (`fc1`-`fc9`) — the same layers `main_loss` trains — and was measurably slowing convergence of the point estimates too, not just the uncertainty head.

The consumer side (`predict.py`/`predict_server.py`/`compare_predictions.py`) also had a mismatched unit: reporting raw `sigma = exp(0.5*log_var)` instead of the Rayleigh-distributed radial error's mean, `sigma*sqrt(pi/2)` — another ~1.25x overstatement on top of the coefficient bug. Both fixed; predicted uncertainty should now be much closer to actual mean landing error (was ~11.1 predicted vs ~1.9 actual before either fix).

**Important:** everywhere "Val Loss" or "Test loss" is reported (in training output, in this document's history section, in `compare_predictions.py`), it means `main_loss` only — the 7-target Huber loss. `uncertainty_loss` is tracked and printed separately, and is folded into the *decision* of which epoch counts as "best" (see 5.5), but the reported loss numbers themselves stay on the same scale as every historical run, so they remain comparable across this whole project's history.

### 5.4 Optimizer / scheduler

`Adam(lr=0.001, weight_decay=1e-4)`. `ReduceLROnPlateau(factor=0.75, patience=55)` — halves-ish the LR when the combined val metric (5.5) stalls for 55 epochs. **The scheduler's patience must be shorter than the early-stopping patience below**, or early stopping fires before the scheduler ever gets a chance to act (this exact bug happened once — see section 8). (Briefly lowered to `15`/`patience=35` to cut wall-clock — measurably undertrained, reverted, see section 8.)

### 5.5 Early stopping

`patience = 175` epochs (briefly dropped to `35` to cut wall-clock — measurably undertrained a real run, reverted; raised past the original `100` to `175` after a `dropout=0.1`-era run firmly plateaued with 100 epochs of zero improvement short of a good result — see section 8 for the full story), `epochs = 50000` cap (early stopping always fires first in practice). The metric watched for both the scheduler and early-stopping is:
```
combined_val_loss = val_loss + val_uncertainty_loss
```
(Originally `val_loss` alone — meaning the uncertainty head could still be actively calibrating, its loss still trending down, when training stopped purely because the point-estimate loss happened to plateau first. Fixed to watch both; see section 8.)

The best-epoch's `val_loss` (main loss alone, not the combined metric) is what gets printed and stored for comparability with history.

### 5.6 Checkpoint format

`torch.save()` to `models/ImprovedNeuralNetwork.pth`, a dict with keys:
```
model_state_dict    (CPU tensors)
input_mean           (CPU tensor, shape (7,))
input_std             (CPU tensor, shape (7,))
```
No `target_mean`/`target_std` keys — targets aren't normalized.

## 6. Known gotchas (read before changing anything)

1. **Editing `ThrowSim.cpp` does nothing on its own.** Changing `throwCount`, a range in `ThrowRanges.h`, or any physics constant requires rebuilding (`make throw_sim` from `build/`) **and** actually rerunning it (`./throw_sim`) to regenerate `throw_results.csv`. This has caused multiple "why isn't my change having any effect" sessions — training silently continues on the old dataset otherwise. Sanity check: `wc -l build/throw_results.csv` should read `throwCount + 1`.
2. **Scheduler patience must be shorter than early-stopping patience.** If not, early stopping can fire before the LR scheduler ever triggers, which measurably hurt results once (5x worse val loss) before being caught and fixed.
3. **Strong wind can prevent an object from ever fully settling** within the 50s cap — wind and ground friction can reach a nonzero steady-state drift velocity instead of true zero. `timeToLand` hits the cap for some windy throws. This is real behavior of the simplified physics model, not a bug.
4. **Bounce counting must filter out resting-frame noise.** The ground-collision branch re-triggers almost every frame once an object is resting (gravity nudges `y` a hair below `ground` each frame), which would inflate a naive bounce counter into the hundreds. Only impacts with incoming `|vy| > 0.5` count.
5. **Output/target column order is a hard contract.** `[final_x, final_y, maxHeight, timeToLand, bounceCount, apexTime, finalVx]` (indices 0–6) must exactly match the column order used everywhere targets are selected from the dataframe, or predictions silently misalign with the wrong physical meaning. Index 7 (uncertainty) has no CSV counterpart and is never selected from the dataframe.
6. **Every script that runs the model must apply `add_engineered_features()` and normalize with the checkpoint's `input_mean`/`input_std`**, in that order. `ThrowGame.cpp` never calls the model directly — it talks to `predict_server.py` over a persistent pipe (see 7.3), so it never has to replicate this logic itself (same reasoning as sharing `Terrain.h`/`ThrowRanges.h`: one source of truth instead of two copies that can drift apart).
7. **`Throwsxx.py` samples the same ranges as `ThrowRanges.h`** — it used to sample wider (e.g. mass up to 90 vs the trained max of 20), which was pure extrapolation with no accuracy guarantee; fixed to match.
8. **`drop_last=True` is required on the training batches.** Without it, a trailing batch can land on exactly 1 sample (whenever the train-set size mod `batch_size` is 1), and `BatchNorm1d` in train mode throws on a batch that small — a real crash, not a warning, that depends on dataset size and so can appear or disappear across otherwise-unrelated changes.
9. **Bigger batches don't automatically mean faster training.** `batch_size=8192` cuts gradient steps per epoch ~4x vs `2048`; scaling `lr` up 2.5x didn't come close to compensating — val loss was still ~35 after 800 epochs (90 min) where `2048`/`lr=0.001` reaches low single digits in under 200. Worse, since `combined_val_loss` was still improving every single epoch, early stopping never triggered — the run was on track for the full `epochs=50000` cap (tens of hours). Always check that early stopping can actually fire under a new config, not just that per-epoch wall time went down.

## 7. The game (`ThrowGame.cpp`)

### 7.1 Window & rendering

`1000×600` fixed **internal** render resolution (everything — 3D scene and HUD — is drawn to an offscreen `RenderTexture2D` at this size), `FLAG_WINDOW_RESIZABLE`, minimum window size `480×300`, `F11` toggles fullscreen. The final composite step scales and letterboxes that fixed-resolution texture to fit whatever the actual window size is — HUD/layout code never has to think about window size, only that one composite step does.

Rendering order per frame: sky gradient (2D rect) → 3D pass (lit terrain model with a custom Blinn-Phong shader, analytically-correct normals from `terrainSlope`, and distance fog fading the terrain into the sky color past the camera; player's guess marker as a translucent disc, target flag, real/predicted flight trails as age-faded "comet" lines, drop-shadow discs under both balls at the terrain height beneath them, the real ball (red) and predicted ball (gold) as lit spheres, a connecting line once both have landed, a particle burst that shrinks and cools from gold to orange over its lifetime) → world-space "YOUR GUESS"/"TARGET" labels projected onto the markers → HUD (card-style panels with a colored accent strip + border, drop-shadow-outlined text since there's no custom font file) → post-process shader pass (vignette + contrast) as the final composite.

Terrain mesh spans `x` from `-150` to `3200` (widened from `±110` — a max-power throw, `VX_MAX`/`VY_MAX`/`MASS_MAX`/`WIND_MAX` together, lands past `x=2600` under the real physics, and was flying off the end of the old, shorter ground). `halfWidth=45` in `z`. Vertex colors are height/slope-tinted (darker green in valleys, warmer highlight near ridges, extra shading on steep faces) instead of a flat single tone.

### 7.2 Controls

```
LEFT/RIGHT       adjust vx           (10 units/s)
UP/DOWN          adjust vy           (10 units/s)
[ / ]            adjust mass         (2 units/s)
A / D            move landing guess  (30 units/s)
SPACE            throw
R                replay last throw's cached trajectory (no new subprocess calls, no re-scoring)
F11              toggle fullscreen
ESC              pause (freezes sim/animation/particles; dims screen; SetExitKey(KEY_NULL) frees ESC from
                 raylib's default quit-key so it can drive pause instead — the window's close button still quits)
TAB              toggle settings panel
right-drag       orbit camera (yaw + height)
scroll wheel     zoom camera (radius)
-  / +           adjust mouse sensitivity (while settings panel open)
I                toggle invert-Y (while settings panel open)
```
Throw-parameter adjustments are locked out while a throw is mid-flight or while paused. `height0` and `windAccel` are **not** player controls — they're randomized fresh each throw (same as the target zone), to keep the control scheme simple. Camera orbit/zoom work even while paused (it's a view control, not gameplay). Mouse sensitivity and invert-Y persist to `game_settings.txt` (repo root) across sessions.

### 7.3 Subprocess bridge

Real physics (unchanged): `./throw_sim --trajectory <vx0> <vy0> <mass> <height0> <windAccel>` → many `"x,y"` lines, one `popen()` call per throw (cheap, no torch).

AI prediction: **not** a fresh `popen()` per throw anymore. `python3 ../predict.py ...` cold-starts a Python interpreter, imports torch, and reloads the checkpoint from disk on *every single call* — hundreds of ms to a couple seconds, dwarfing the actual forward pass. Instead, `startPredictServer()` forks `predict_server.py` once at game launch (manual `pipe()`+`fork()`+`exec()`, since `popen()` is one-directional and can't do a persistent bidirectional pipe) and keeps it alive for the game's lifetime; `predictThrow()` writes one line, reads one line back, per throw — the model loads exactly once. `signal(SIGPIPE, SIG_IGN)` is set at startup so a dead server on the other end of the pipe fails the next write gracefully (`predictThrow` returns `false`) instead of taking the whole game down.

`predict_server.py`'s response line is parsed with a full 8-field `sscanf` into `predX, predY, predMaxHeight, predTimeToLand, predBounceCount, predApexTime, predFinalVx, predUncertainty` — all 8 model outputs, not just x/y, are kept and shown (see 7.6). If the server never started or a call fails, the game shows a fallback message instead of crashing — never treats a missing prediction as fatal.

Every real throw (not `R` replays) also runs `./throw_sim <vx0> <vy0> <mass> <height0> <windAccel>` (single-row mode, no trajectory) to get the authoritative final row — `bounceCount`/`apexTime`/`finalVx` aren't recoverable from trajectory position samples alone — and appends it to `game_throws.csv` (see 7.7).

### 7.4 Animation

The real ball plays back `throw_sim`'s step-by-step trajectory at `2.5×` real-time speed, with pausing tracked via accumulated paused-duration so `ESC` genuinely freezes the animation rather than just the input handlers. The predicted ball has no real trajectory (the model only predicts the endpoint) — it flies on a synthetic parabolic arc from `height0` to `(predX, predY)`, timed to land simultaneously with the real ball.

### 7.5 Scoring & persistent stats

Once both the real and predicted landing are known: `aiError` = Euclidean distance between them; `playerError = |realX - guessX|`, player wins the round if their error is smaller; `target score += max(0, 100 - |realX - targetX|)`. Running stats (throw count, average/best/worst AI error, a streak counter for consecutive throws under 1.0 unit of error, player-vs-AI win tally, cumulative target score) are saved to `game_stats.txt` at the **repo root** (not inside `build/`, so a build wipe doesn't erase progress) immediately after every scored throw, as plain `key value` lines, loaded back on startup.

### 7.6 Full AI-output HUD panel

Top-right panel shows every model output, not just x/y: `x, y, maxHeight, timeToLand, bounceCount, apexTime, finalVx` real-vs-AI side by side (real values come from the same single-row `throw_sim` call used for `game_throws.csv` logging, so this is a genuine ground-truth comparison, not just the prediction alone), plus the uncertainty line (`~X.XX avg error`, phrased as an average rather than a "68% confident" claim — see 5.3, the corrected quantity is a Rayleigh-distribution mean, not a symmetric confidence-interval bound, so the old "68% confident" wording overclaimed precision it didn't have).

### 7.7 Training on played throws

Every real throw (not replays) is appended to `game_throws.csv` (repo root) in the same 12-column schema as `build/throw_results.csv` — see 7.3. `main.py`/`kfold_eval.py` concatenate it onto the synthetic dataset automatically if the file exists (section 5.1). Nothing trains *during* play — the model stays frozen for inference the whole session (`predict_server.py` never calls `.backward()`); playing more throws only grows the log, it's a fresh `python3 main.py` run that actually incorporates them into the checkpoint.

## 8. Improvements log (chronological history, with real numbers)

Architecture evolution (each version is the same file, `models/ImprovedNeuralNetwork.py`, getting wider/deeper over time):

| Version | Hidden layers | Params | Notes |
|---|---|---|---|
| v1 | 1 (16 neurons) | — | Original prototype |
| v2–v6 | 2 to 4 | — | Progressive widening/dropout tuning |
| v7 | 6 | — | LR scheduler added |
| v8 | 6 (250,250,250,300,450,600) | 614,103 | Best result on the original 3-output task: MAE x=1.129, y=1.038, h=0.445 |
| v9 | 8 (…,1200,2000) | 3,747,903 | Added maxHeight/timeToLand/bounceCount/apexTime/finalVx (7 outputs), height0/windAccel inputs |
| v10 (current) | 9 (…,2000,2000) | 7,764,408 | Added the uncertainty output (8th) |

**Early story (10000-row dataset, 3-output task, most historically instructive):**

First real training run (v2 arch, 1000 throws, no val split): loss `215.10`. More epochs: `5.20` (plateaued). Manual LR tuning: `0.32`. Then the train/val split was added for the first time — train `0.29`, **val `6.46`**. That val loss was the real turning point: train loss looked great the whole time, but the model was just memorizing the training rows.

Input normalization (vx0/vy0/mass were on wildly different scales): val loss **`0.056`** — ~115x improvement from one change. Terrain variance added (harder target): `0.076`. Early stopping added: more reliable, same ballpark.

Then a real bug was caught: `ThrowSim.cpp`'s throw count had been bumped 1000 → 5000 → 10000, but the dataset file was never regenerated after the first bump (see gotcha #1) — every "bigger dataset" result up to that point was still trained on the original 1000-row file. After the fix: val loss **`0.0114`**, MAE x=0.104, y=0.038 on the real 10000-row data. 5-fold CV confirmed it: mean `0.0105`, std dev `0.0013` — tight, not a lucky split.

**Scaling up (50000-row dataset, still 3-output):**

Scaled to 50000 rows: val loss `13.32 → 7.20`. First LR scheduler attempt was too aggressive (patience=15, factor=0.1) and made things measurably *worse* (`10.59` vs the `7.20` baseline) — retuned (factor=0.69→0.75 over a few iterations, patience=35→55) and combined with widening the network to v8: val loss `3.24` → eventually the v8 best of MAE x=1.129, y=1.038, h=0.445, all three metrics improved together, no tradeoff.

Two things tried and **reverted** here because they measurably hurt results: normalizing the targets (fixed y's starved gradient, but tripled x's error) and weighted loss on top of that (still worse than plain unweighted Huber). Verified via `compare_predictions.py` and reverted when the numbers said so, not just abandoned on a hunch.

**Expanding the task (7 outputs, height/wind inputs, uncertainty head):**

Added `maxHeight`/`timeToLand`/`bounceCount`/`apexTime`/`finalVx` as 4 more outputs (7 total), then `height0`/`windAccel` as 2 more inputs (6 total with the engineered feature). Scaled to 500000 rows: val `7.20 → 0.4262`, MAE x=1.129→0.969, y=1.038→0.168 (6x better), h=0.445→0.640 (slight regression) — net win, on a genuinely harder task (more to predict, wider input space).

Then the uncertainty output was added. First mini-batch/MPS run had the scheduler-patience-vs-early-stopping bug (gotcha #2): scheduler patience 55 > early-stop patience 50, so early stopping fired before the scheduler got real room to act — 79 epochs, val loss `2.03`, clearly undertrained. Fixed (early-stop patience raised to 100/150 across iterations, always kept longer than the scheduler's 55): `928` epochs, val loss **`0.4262`**, test `0.4321` — the fix alone was a 5x improvement, bigger than several actual feature additions combined.

Scaled to 1000000 rows and also fixed early-stopping/scheduler to watch `val_loss + val_uncertainty_loss` combined (not `val_loss` alone) so the uncertainty head gets a real chance to finish calibrating: **best val loss `0.2968`, test loss `0.3019`** — close agreement, honest, currently the best result on this (much harder) 7-output task.

`compare_predictions.py`'s calibration check on an earlier uncertainty checkpoint: predicted-uncertainty vs actual-landing-error correlation of `0.616` — meaning the uncertainty head learned something real (it's not random), though it was running about 3x too cautious on average (predicted std `14.978` vs actual mean error `5.230`) at that point, consistent with training having stopped before full calibration (which the combined-loss fix above directly addresses).

Later, on the 700000-row dataset with the fixed early-stopping/scheduler relationship: correlation improved to `0.805`, but the predicted-std/actual-error *ratio* was still badly off (`8.864`-`11.109` predicted vs `1.897` actual — 4.7-5.9x too cautious), which turned out to be two separate, compounding bugs rather than just "needs more epochs" — see the next entry.

**Uncertainty-loss bug fixes (this session).** Two real bugs found in `uncertainty_loss`, both explained in full in section 5.3: the `log_var` term had the wrong coefficient for a 2D (not scalar) Gaussian NLL (~sqrt(2)x overstatement), and the consumer scripts reported raw `sigma` instead of the Rayleigh-mean (`sigma*sqrt(pi/2)`, another ~1.25x). Combined, roughly explains the observed ~4.7-5.9x gap. Also added `log_var` clamping (`±10`) after discovering the unclamped loss could spike to `~4.6e8` in the first 20 epochs and (since `log_var` isn't detached) drag down convergence of the point-estimate outputs too, not just the uncertainty head — this was likely part of why even `val_loss` alone had historically taken so many epochs to converge. Also fixed: dropout was `1e-10` (effectively disabled, a typo) on every hidden layer, now `0.1`; `drop_last=True` added to training batches (a trailing batch of exactly 1 sample crashes `BatchNorm1d` in train mode — a landmine tied to dataset size, not yet hit but real).

**Training-speed experiment (batch_size/lr).** Benchmarked replacing the `DataLoader` with manual on-device batching (`~15%` faster/epoch, no effect on convergence — kept) and separately tried `batch_size=8192`+`lr=0.0025` to cut wall-clock further. That combination measurably backfired: `~4x` fewer gradient steps per epoch, and the higher `lr` didn't compensate — `val_loss` was still `~35` after 800 epochs (90 min) where `2048`/`0.001` reaches low single digits well under 200 epochs, and since `combined_val_loss` was still improving every single epoch, early stopping never fired — on track for the full `50000`-epoch cap. Reverted to `2048`/`0.001`; kept the on-device batching change and lowered `patience` `100→35` / scheduler `patience` `55→15` instead, which bounds worst-case wall time without needing a batch-size change that alters convergence dynamics.

**Physics-informed `final_x` baseline (Experiment A — tried, reverted).** `final_x` was consistently the model's weakest output relative to the others — MAE `1.871` vs `y`'s `0.178` on the 30-throw eval set, with absolute error growing at large `|x|` (e.g. `10.423` error at `real_x≈1322.8`, though the *relative* error, ~0.2-0.8%, is fairly stable). Added `physics_baseline_x` (section 4.1) as a second engineered feature alongside `x_inf`, widening `fc1` `6→7` — the smallest change that could test whether the network benefits from an explicit wind-aware analytical estimate. Baseline-alone sanity check before training anything: `physics_baseline_x` vs true `final_x` on the same 30 throws = MAE `~74.5` — a weak standalone predictor (ignores bounce/friction/settling), leaving open whether the network could still extract value from it as a feature.

**Result: it regressed every output, not just x** — `x` `1.871→4.979`, `y` `0.178→0.475`, `maxHeight` `0.404→3.235`, all worse. Confounded with `patience=35` (a separate speed change made the same session, see the training-speed entry above) likely cutting training short before real convergence, so this isn't a clean verdict on the feature itself. **Reverted**: `fc1` back to 6 inputs, `physics_baseline_x` no longer called from `add_engineered_features()` (the function stays in `features.py`, unused, for a future retry that isolates this one variable properly — same patience/dropout as whatever config is currently proven, not a config being changed at the same time).

**A second, serious problem surfaced attempting this experiment: the actual best checkpoint (val loss `0.2968`, test `0.3019`, `final_x` MAE `1.871`) was never committed to git**, and the experiment's training run overwrote `models/ImprovedNeuralNetwork.pth` directly (as `main.py` always does) before that number could be verified as beaten or reverted from. That checkpoint is unrecoverable. Recovered to the last git-committed checkpoint (`final_x` MAE `5.178`) as a safe floor, then ran two further retrains chasing the lost accuracy back: one with `dropout=0.1` (the just-fixed value, `1e-10→0.1`, being exercised for the first time — patience=100, early-stopped at epoch 455, val loss `1.5698`, but `final_x` MAE `11.680`, worse) and one with `dropout=0.05`/`patience=175` (val loss `1.1224`, `final_x` MAE `7.634`, still worse than the `5.178` floor). Both landed worse on `x` specifically despite lower *combined* val loss — the combined Huber loss across 7 outputs doesn't guarantee `x` specifically improves; it can trade `x` accuracy for the other 6.

**Root cause found: dataset size.** The `0.2968`/`1.871` checkpoint was trained on **1,000,000 rows**; `ThrowSim.cpp`'s `throwCount` had drifted down to `700,000` sometime after that run (also the source of a real CV-accuracy mismatch — the CV's "1,000,000+ simulated throws" claim didn't match what was on disk). `x` has by far the widest dynamic range of any output, so it's the most data-hungry — the likeliest explanation for why `y`/`maxHeight`/etc. converged fine on 700k rows while `x` specifically suffered. Regenerated the full 1,000,000-row dataset (`throwCount` bumped back to `1000000`, rebuilt, reran `./throw_sim` — takes seconds, it's the C++ simulator, not training) and retrained on it with `dropout=0.05`/`patience=175`: **val loss `0.9621`, test `0.9647`, `final_x` MAE `4.258`** — a genuine, verified improvement over the `5.178` floor (also beats it on `y` `0.303` vs `0.431`, `maxHeight` `1.441` vs `2.571`, `bounceCount` `1.012` vs `1.347`, and uncertainty correlation `0.757` vs `0.616`), deployed. Still short of the lost `1.871`/`0.2968` result — dataset size looks like the dominant lever, but isn't the whole gap; more training time and/or revisiting the `physics_baseline_x` feature (now with the dataset-size confound removed) are the next things to try, not attempted yet as of this doc update.

**Safety net added because of this incident**: `main.py` now saves the checkpoint on every validation-loss improvement, not just at the end of training — a run that gets cut short (or killed) no longer risks leaving a worse or absent checkpoint deployed than what was there before it started.

## 9. What actually moved the needle, ranked

1. **Fixing the stale-dataset bug** (gotcha #1) — recurred multiple times. Bigger architecture and "more data" did nothing until the data was actually real.
2. **Fixing the scheduler/early-stopping patience relationship** (gotcha #2) — a one-line config bug cost 5x on val loss, bigger than several feature additions combined.
3. **Input normalization** — 115x improvement from one change.
4. **Adding the train/val split** — didn't improve anything by itself, but revealed the model was overfitting badly, which is what made every subsequent fix possible to evaluate honestly.
5. **Scaling the dataset up** (1000 → 10000 → 50000 → 500000 → 1000000), each time genuinely regenerated.
6. Architecture widening, dropout tuning, mini-batching, MPS. Real, incremental gains — smaller than the items above.
7. **Target normalization and weighted loss** — tried, measured, reverted when the numbers said they hurt. Knowing when *not* to keep a change is as much a skill as making one.
8. **The uncertainty-loss coefficient/clamping bugs** (section 8) — not just a cosmetic "uncertainty is a bit off" issue: the unclamped version was spiking to `~4.6e8` early in training and, since it isn't detached, was measurably fighting the main loss's gradient through the shared trunk.
9. **`batch_size=8192`/`lr=0.0025` — a real counterexample.** Bigger batches + scaled `lr` is a common "free speedup," and here it wasn't: fewer gradient steps per epoch outweighed the per-step wall-clock win, and because the loss curve never stopped improving, patience-based early stopping — the exact safety net meant to bound runaway training time — never engaged. Logged here because it's a specific, measured case of a generally-reasonable-sounding optimization failing, not because bigger batches are bad in general.
